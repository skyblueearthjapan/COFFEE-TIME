# AI DUEL 実装計画（v1・2026-09-22）

設計書 `参考データ/ゲーム4部作/COFFEE_TIME_AI_DUEL_Design_v1.0.md`（以下「設計書」）を読んだうえで、
**この端末の実情に合わせて何を作り、何を作らないか**を決めた記録。実装・レビューはこの文書を正とする。

## 1. ひとことで

じゃんけん 10 回勝負。AI は「あなたの次の手」を過去の記録から予測し、先に手を決めてから勝負する。
予測は Wi-Fi があれば Jev（GAS 経由）、無ければ端末内の統計 AI。記録は人ごと（アイコンごと）に端末へ残り、次回の予測に使われる。

## 2. 設計書から変えたところ（ディレクター判断）

設計書は「GAS + スプレッドシート 9 枚 + 11 操作 + PIN + コミットハッシュ」を前提にした大掛かりなサーバー型。
この端末は **持ち運び・Wi-Fi は iPhone テザリングのときだけ・GAS 往復 1.6〜3.3 秒** なので、次のように軽くする。

| 項目 | 設計書 | v1 の実装 | 理由 |
|---|---|---|---|
| 個人履歴の正本 | スプレッドシート | **端末 (NVS)**。オンライン時はシートにも 1 行ずつ写す | Wi-Fi が無い日でも「その人の癖」で遊べる。1 回戦 20 往復の待ちも無くなる |
| 本人の選び方 | PC で登録 + ニックネーム + 6 桁 PIN | **8 つのアイコンから自分のものを選ぶだけ**（+ ゲスト） | 端末に日本語入力が無い。名前も PIN も持たないので個人情報ゼロ |
| AI の手の確定 | GAS が決めてハッシュで後出し防止 | **端末が予測を受け取った時点で確定**し、確定するまで手のボタンは無効 | 端末 1 台の中で完結するのでハッシュ照合の意味が無い |
| Jev の呼び方 | GAS が状態を組み立てる | **端末が状態(集計)を作り、GAS は Jev へ中継して検証**するだけ | GAS 側にデータベースを持たない |
| 待ち時間 | prepare → submit の 2 往復 | **結果を見ている間に次の回の予測を先読み**（1 回 1 往復） | 体感の待ちをほぼ無くす |
| モード選択 | Jev / 統計 AI を選ぶ | **自動**（つながれば Jev、だめなら統計 AI）。どちらで戦ったかは毎回表示 | 画面を 1 枚減らす |
| オフライン | 個人記録に入れない | **入れる**（正本が端末なので区別する理由が無い）。シートには残らない | |

守るもの（設計書どおり）: 勝敗表、10 回固定・あいこも 1 回、勝つ手の選び方（期待得点差の最大化。§5.4）、
統計 AI の式（§5.1）、統計の構造と「対戦の境界を越えて遷移を数えない」(§4.3)、癖の表示条件（§4.5）、
Jev に名前・杯数・今回の手を送らない（§5.2）、Jev 1 回戦 1 ラウンド最大 1 呼び出し、初回（記録 0）は Jev を呼ばない（§5.3）、
Jev が使えなかった回を Jev の成績に入れない、途中終了は負けにしない、手は `LV_EVENT_CLICKED` で 1 回だけ確定。

作らないもの: PIN・セッション・管理画面・9 枚のシート・コミットハッシュ・再開 (resume)・複数端末対応。

## 3. 画面の流れ

```text
ゲーム一覧 → AI DUEL
  entry     「AI DUEL」「あなたの次の一手を読めるか」  [はじめる] [あそびかた]
  players   8 つのアイコン（2 段 × 4）+ [ゲスト]        アイコンの下に累計ラウンド数
  profile   選んだアイコン / 対戦 n 回（勝・負・分）/ 記録量レベル
            [対戦する] [癖を見る] [記録を消す(長押し)] [もどる]
  intro     「10 回勝負。相手は先に手を決めます」 [はじめる]
  choose    n/10、スコア、グー・チョキ・パー。AI の手が決まるまでは「相手が考え中…」でボタン無効
            決まったら「相手の手は確定済み」+ 相手の種類（Jev / 統計AI）
  result    両者の手、勝敗（あなたの勝ち！/ Jevの勝ち！/ 統計AIの勝ち！/ あいこ）、
            「相手の予測：グー 52%」、現在のスコア [次へ]
  summary   10 回の勝敗、勝者、Jev / 統計 AI の内訳 [もう一度] [癖を見る] [おわる]
  habits    最大 3 枚の統計カード（設計書 §4.5 のテンプレートと優先順）
  paused    放置で一時停止（既存ゲームと同じ作法）
  confirm   途中終了の確認「途中終了しますか？確定済みの記録は残ります」
```

- アイコン 8 種: カップ / まめ / ほし / つき / たいよう / はっぱ / くも / はぐるま（アイコンフォントで描く。絵文字は使わない）。
- 手のアイコンは図形フォント + 「グー / チョキ / パー」の文字。
- 記録量レベル: 0 / 10 / 50 / 200 ラウンドの区切り（「AI 理解度 ○%」のような表示はしない）。
- ゲストは記録を残さない（その対戦の中だけ統計を使う）。文言「今回だけの記録です。次回には引き継ぎません」。
- 10 回終わったら `cup::stats::gamePlayed(cup::GameId::Duel, …)` を 1 回。途中終了では数えない。

## 4. 端末のデータ

- NVS 名前空間 `ct_duel`。キー `p0`〜`p7` に 1 人ぶんの統計 blob（版数つき・数百バイト）、`meta` に対戦通し番号など。
- blob の中身は設計書 §4.2 と同じ項目（rounds, hand_counts, outcome_counts, first_hand_counts, transition_by_hand,
  transition_by_hand_result, repeat_after_result, tail 50 件, prediction(jev/stats の n・hits・brier_sum・nll_sum), match_counts）。
  tail の `match_id` は 32 桁 ID の代わりに端末内の対戦通し番号 (u16) を使う。
- 保存は 1 ラウンド確定ごと（電源断でも確定済みは残る）。読み込み失敗・版数違いは空の統計として扱う（消さずに上書きもしない → 次の保存で新形式）。
- 途中終了・放置終了は `match_counts.aborted` を 1 回だけ増やす。

## 5. 予測の流れ（1 ラウンド）

1. 前のラウンドの結果を出した瞬間（第 1 回は intro を開いた瞬間）に、次の回の準備を始める。
2. 端末内で統計 AI の確率 `baseline` を計算する（必ず成功する）。
3. 条件がそろえば GAS へ予測を頼む: Wi-Fi 接続中 かつ その人の rounds ≥ 1（ゲストはその対戦内の回数）かつ GAS_URL あり。
4. 返事が**依頼から 9 秒以内**に届き検証に通れば Jev の確率を採用、さもなければ baseline を採用。
   採用した確率から期待得点差が最大の手を選ぶ（同点は `esp_random()` で等確率）。**いちど決めた手は変えない**。遅れて届いた返事は捨てる（依頼番号で照合）。
5. 手のボタンを有効にする。プレイヤーが押したら即座に勝敗を出し、統計を更新・保存し、1. に戻る。

通信は LVGL のタスクの中で行わない。`net::` に「依頼を 1 件だけ預けて、結果をあとで受け取る」口を作り、
メインループ側（既存の `net::poll`）で送受信する。エスパー第 2 段階でも同じ口を使えるよう、ゲームに依存しない形にする。

## 6. 端末 ⇔ GAS の約束（`event: "duel"`）

要求（端末 → GAS。`token` と `device` は NetService が足す）:

```json
{
  "event": "duel",
  "req": 1234,
  "state": { …設計書 §6.1 の state と同じ形… },
  "log": { "player": "p3", "match": 12, "round": 4,
           "you": "ROCK", "ai": "PAPER", "result": "ai_win", "provider": "jev" }
}
```

- `state` があれば Jev に予測を頼む。無ければ記録だけ。
- **記録は対戦の終わり（10 回終了・途中終了）に `"logs": [ … ]`（最大 10 件、各要素は上の `log` と同じ形）でまとめて 1 回送る。**
  ラウンドごとの要求には `state` だけを入れる。GAS は POST の返事（302）を返す前に全部の処理を終えるので、
  毎回シートに書くと返事が 4〜6 秒になり、端末の待ち時間に間に合わなかった（2026-09-22 実機で 8 回中 8 回が統計 AI に落ちた）。
  GAS は `DuelRounds` シートに行を足す（無ければ作る）。ゲストは `"player": "guest"`。単発の `log` も受け付ける（試験用）。
- 送れなかった記録（圏外・通信中）は捨てる。正本は端末なので遊びには影響しない。
- 端末側の待ち: POST 6.5 秒 + 転送先 GET 5 秒。ゲーム側は依頼から 9 秒で見切って統計 AI に決める。
- `state` の中身: `game, round_no, history_rounds, overall_counts, recent20_counts, first_hand_counts,
  previous_round(null 可), conditional_next_counts{by_hand, by_hand_result: sample_n + 3 手}, recent_sequence(最大 12 件:
  new_match, history_truncated, round_no, player_hand, ai_hand, player_result), same_hand_streak, stats_baseline, notice`。
  **入れてはいけないもの**: アイコン名・端末名・杯数・今回の手・未公開の AI の手。

応答（GAS → 端末）:

```json
{ "ok": true, "req": 1234, "provider": "jev", "p": [0.41, 0.33, 0.26], "confidence": 0.41, "ms": 310 }
{ "ok": true, "req": 1234, "provider": "none", "reason": "HTTP_429" }
```

- `p` は ROCK / SCISSORS / PAPER の順。GAS 側で設計書 §6.2 の検証（3 キーちょうど・有限・0〜1・合計 1±0.001）を済ませ、正規化して返す。
- `provider: "none"` のとき端末は統計 AI を使う。理由は `NO_KEY / HTTP_xxx / BAD_JSON / INVALID / DAILY_LIMIT / TRANSPORT`。
- GAS は 1 日の Jev 呼び出し回数を数え、スクリプト プロパティ `JEV_DAILY_MAX`（無ければ 1500）を超えたら `DAILY_LIMIT` を返す。

## 7. 検査

- `firmware/src/app/games/duel/core/duel_core.hpp`（ヘッダーだけ・Arduino 非依存）を zig でホスト用にコンパイルして検査する
  （`tools/duel_checks.cpp` + `tools/run_duel_checks.py`。エスパー・人狼と同じ作法）。
- 設計書の参考ロジック `duel_reference.py` で作った正解データ（乱数列 → 統計・予測確率・最善手の集合）と 1e-9 以内で一致すること。
  `test_vectors.json` の「最多手に勝つだけでは最善にならない例」も通すこと。
- 実機は `tools/uiwalk.py` で 1 対戦を通し、シリアルの開発用表示で状態を確認する。

## 8. 残すもの（v1 の外）

- ニックネーム表示（SD のファイルから読む案）、9 人以上、PIN。
- オフライン中のラウンドをあとからシートへ送る仕組み。
- Jev と統計 AI の成績比較の画面（数字は blob に貯めてある）。
