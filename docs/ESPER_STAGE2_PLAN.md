# エスパー対決 第 2 段階（Jev）実装計画（2026-09-23）

第 1 段階（端末だけのルール方式・4 モード）は済み。設計書 `参考データ/ゲーム4部作/COFFEE_TIME_AI_ESPER_Design_v1.0.md` §3.5〜3.7・§4 を読んだうえで、
AI DUEL・リバーシ・POKER TABLE で確立した「依頼箱 + GAS 中継 + 自動やり直し」の作法で Jev をつなぐ。ユーザーは「やらないとまずい」と確認済み。

## 1. Jev の役割（設計書どおり）

- 候補の絞り込み・情報量の計算・安全な質問（最大 8 問）の抽出は**今までどおりコード**（`core/esper_core.hpp`）。
- Jev は 1 回の呼び出しで 2 つを選ぶ: **次の質問**（安全な最大 8 問の中から。2 問以上あるときだけ）と**最終予想**（残った候補の中から）。
- 送ってよいのは: ルール版・モード・有効な回答履歴（質問の英語の意味 + yes/no）・残った候補（英語名 + 日本語の定義）・安全な質問（英語の意味）・残り問数。
  **送らないもの**: 頭の中の答え、一覧で見たカード、メモ（`s_memo`）、滞在時間、社員名、コーヒーの履歴。
- Jev の返事は検証（候補が一覧にある・確率のキーが一致・有限で 0〜1・合計 1±0.001）し、だめなら黙ってルール方式（基準質問の先頭 / seed で 1 つ）へ戻す。
- 画面の「AI の予想 42%」は Jev の確率があるときだけ。ルール方式のときは候補数を出す（設計書 3.7）。処理系の名前は `jev` / `mixed` / `rule` を混ぜない。

## 2. ディレクター判断（設計書から変えるところ）

| 項目 | 設計書 | 実装 | 理由 |
|---|---|---|---|
| サーバー | 新規 Python サーバー（9 エンドポイント・セッション DB） | **GAS の `event:"esper"` 1 操作**。セッションは端末が持つ | 端末 1 台。AI DUEL・リバーシ・POKER TABLE と同じ |
| 候補・質問の英文 | 端末が state に入れて送る | **端末は ID だけを送り、GAS が `EsperCatalog.gs`（catalog.json から生成）で英文に置き換える** | 端末のフラッシュに英文 20KB を足さない。Jev に届く state は設計書どおりの形 |
| 待ち時間 | 1 回 3 秒 | **回答の直後に「AI が考え中…」を最大 8 秒**。届かなければ基準質問（もう決めてある）をそのまま出す | GAS の往復は 4〜7 秒。先読みは回答が分からないと作れない（質問ごとに 1 往復） |
| 呼び出しの回数 | 質問に答えるごとに 1 回（6〜11 回/遊び） | 同じ。候補が 1 つ・安全な質問が 1 問のときは呼ばない（設計書 4.3） | |
| 同じ局面の再送 | セッション DB | GAS の控え（セッション ID + revision + 履歴のハッシュ。10 分） | |

## 3. 端末側の流れ（1 問）

1. 人間が はい／いいえ／わからない を押す → コアが候補を絞り、安全な質問一覧（shortlist）と基準質問を決める（今までどおり。基準 = 先頭）。
2. 候補が 2 つ以上あり、Wi-Fi があり、`GAS_URL` があれば、`{ session, rev, mode, history, candidates(ID), shortlist(ID), remaining }` を依頼箱で送り、画面は「AI が考え中…」（コーヒーのボタンは生きている）。
3. 8 秒以内に返事が来て検証に通れば、コアの `applyAdvice(question_id, guess_id, guess_p)` で**表示前に**質問を差し替える（最終予想の局面なら予想を差し替え、「AI の予想 n%」を出す）。
   来なければ基準のまま出す。遅れて届いた返事は req 番号と revision で捨てる。1 回だけ自動でやり直す（AI DUEL と同じ）。
4. 取り消し（undo）・わからない で局面が変わったら、進行中の依頼は捨てる。
5. 1 回の遊びで Jev を 1 回でも使い、途中でルール方式に落ちたら処理系は `mixed`。1 回も使えなければ `rule`。結果画面と記録に出す。

## 4. GAS（`gas/Esper.gs` + `gas/EsperCatalog.gs`）

```json
要求: { "event":"esper", "req":12, "session":"<32hex>", "rev":5, "mode":"regular",
        "history":[{"q":"Q001","a":"yes"},{"q":"Q014","a":"no"}], "candidates":["D01","D04",…], "shortlist":["Q005","Q021"], "remaining":3 }
応答: { "ok":true, "req":12, "status":"ready", "question":"Q021", "guess":"D04", "guess_p":0.42, "top":[["D04",0.42],["D01",0.31],…5 件], "ms":320, "cached":false }
      { "ok":true, "req":12, "status":"failed", "reason":"NO_KEY|DAILY_LIMIT|BAD_IDS|PROVIDER_HTTP_429|…" }
```

- GAS は ID を検証（カタログにある・重複なし・候補 ≤ 128・shortlist ≤ 8）し、設計書 4.4 の形で Jev を 1 回呼ぶ（`guess` + 2 問以上なら `next_question`）。
- 返事は 768 バイトの受け口に収まるよう、確率は上位 5 件だけ返す。
- 1 日の上限は他ゲームと共通（`JEV_DAILY_MAX`）。成功した呼び出しだけ数える。

## 5. 検査

- `run_esper_checks.py` の手本 168 局は LocalAdvisor のまま（決定性を保つ）。`applyAdvice` の検査を足す（一覧外の質問・候補外の予想は無視される、revision が違えば無視、Jev 有りで手本が変わらない）。
- GAS は Node の模擬試験（ID の検証・控え・失敗理由）。端末の要求 JSON をそのまま通す。
- 実機: `uiwalk.py` で 1 局（`expect:V:` で状態確認）。JEV / ルールの表示、通信失敗時の落ち方、メモが送られていないことをログで確認。
