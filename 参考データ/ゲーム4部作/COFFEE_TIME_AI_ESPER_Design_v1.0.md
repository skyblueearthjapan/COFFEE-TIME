## 1. ゲームのルール

### 1.1 プレイヤーの流れ

`HOME → GAME → モード選択 → 候補一覧 → 頭の中で1つ決める → 決めた → 質問とYes/No → 最終予想 → Yes/Noで正解確認 → 結果 → HOME`

開始時の説明文は次の固定文とする。

> 一覧の中から1つだけ、頭の中で決めてください。答えは入力しません。説明にある温度や材料も、そのまま思い浮かべてください。途中で別のものに変えず、質問に正直に答えてください。

「コーヒー一般」ではなく「ホットブラック」などのカードを選ぶ。メニューにない対象を自由に思い浮かべるモードはv1には入れない。

### 1.2 勝敗と終了条件

| 条件 | 画面 | サーバー上の結果 |
|---|---|---|
| 最終予想にYes | `AIの勝ち！ 当てられました。` | `ai_win` |
| 最終予想にNo | `あなたの勝ち！ 今回は当てられませんでした。` | `human_win` |
| ルール対戦でYes | `端末の勝ち！` | `ai_win`、ただし集計区分は`rule` |
| 質問途中で終了 | `また遊んでください` | `aborted`、勝敗母数から除外 |
| 無操作・期限切れ | HOMEに戻る | `expired`、勝敗母数から除外 |
| 対象が一覧になかったと後から申告 | `今回は集計対象外です` | `invalid_target`、勝敗母数から除外 |
| 結果をサーバーへ送れない | `結果は端末に保存しました` | オンライン中のセッションなら再送待ち。オフライン開始なら端末内集計のみ |

正解はユーザーの自己申告である。端末は頭の中の答えを検証できない。「AIが嘘を見抜いた」「知能を測定した」と表示しない。最終予想は1つだけで、Noの後に第2候補で再挑戦して勝ちを取り直さない。

### 1.3 質問数の根拠と難易度

Yes/Noをk回聞いた場合、回答列は最大`2^k`通り。5問では32通りであり、128候補を常に一意に当てる保証はできない。これは分岐数の計算で、Jevの性能や速度では解消しない。実用的な質問には偏りがあるため、`ceil(log2(N))`は下限であって、その問数で必ず終わるという意味ではない。

| モード | 対象 | 上限 | 目標プレイ時間（設計目標） |
|---|---|---:|---|
| EASY | 指定した飲み物8種類 | 5問 | 20〜45秒 |
| NORMAL | 飲み物32種類 | 7問 | 30〜60秒 |
| HARD | 全4分野・128種類 | 10問 | 45〜90秒 |

候補が1つなら早めに予想する。候補数が増えるモードを難易度と呼ぶが、人間の知能の優劣を評価するものではない。同じ候補・同じ回答・同じ設定なら、質問順が同じになる場合もある。毎回必ず変わるとは保証しない。

### 1.4 詰まりを避ける操作

- **わからない：** HELP内に置く。回答履歴には`skip`として保存し、候補を除外しない。Yes/No回答の上限を消費しない。同じ質問を再出題せず、最大2回まで。2回を超えたら「今の情報で予想」「終了」を選べる。
- **1つ戻る：** 最後のYes/No回答を1つ取り消し、取り消した質問を再表示する。画面上の質問数と候補集合を履歴から再計算する。回数は最大2回。過去回答を任意に編集する画面はv1では作らない。
- **最終予想前のやり直し：** 予想画面のHELPでも1つ戻れる。ただしYes/Noで勝敗を確定した後は回答履歴を変更しない。
- **無操作：** 45秒で減光、120秒でゲームを終了してHOME。HELPを開いて操作している時間は無操作に数えない。サーバー側のセッション最大寿命は開始から15分。

スキップや誤回答がある場合は一意に当てられないことがある。救済操作を含む実プレイの正解率を、規範回答のシミュレーション結果と混同しない。

## 2. データの範囲と定義方法

### 2.1 4分野

| 接頭辞 | 分野 | 件数 | ID |
|---|---|---:|---|
| D | 飲み物 | 32 | D01〜D32 |
| F | カフェの食べ物 | 32 | F01〜F32 |
| O | カフェ・デスク用品 | 32 | O01〜O32 |
| T | 工場の道具・保護具・締結部品 | 32 | T01〜T32 |

128候補は全モード共通のカタログに収める。EASY/NORMALはIDによる部分集合であり、同じ物に別IDを発行しない。HARDは全128候補。個人名、病気、宗教、政治、危険行為、社員の能力・性格を対象にしない。道具のカードはゲーム用の形と用途の説明であり、作業手順や保護性能の保証ではない。

### 2.2 正確さの扱い

候補の説明は、世界のあらゆる製品についての科学的断定ではなく、**このゲームで思い浮かべるカードの仕様**である。例えば「アイスミルクティー」は本書では加糖、「アイスラテ」は無糖とする。商品や家庭のレシピの違いをAIが勝手に補正してはいけない。

色を尋ねるときは飲み物の中身を対象にし、カップや包装の色は除く。主な温度をカード名で固定し、ホットとアイスを曖昧にまとめない。味や形が分からない時はヘルプまたはスキップで進める。

「おいしい」「健康によい」「高価」「疲れている人向き」など、個人差や評価が中心になる質問は採用しない。カフェイン量やアレルゲンを当てるゲームにはせず、食事・健康判断へ流用しない。

### 2.3 項目スキーマ

**Item**の全フィールドは`id / group / name_ja / name_en / definition_ja`。いずれも必須で空文字不可。`group`はD/F/O/T。UI表示には`name_ja`、モデルの候補識別にはIDと`name_en`を使う。表記ゆれは入力受付しないため、自由入力用の別名辞書はv1で不要である。

**Question**の全フィールドは`id / text_ja / meaning_en / scope_groups / yes_ids / help_ja / family`。いずれも必須。`id`はQ001など、`text_ja`は日本語表示、`meaning_en`はモデルへ渡す意味、`scope_groups`は適用分野、`yes_ids`はYesになる全候補ID、`help_ja`は補足、`family`は質問の意味を示す識別子。v1では各familyは質問IDと同じである。

### 2.4 18,688セルの完全な対応規則

128候補×146問＝**18,688組**について、以下の規則で答えが一意に定義される。

```text
対象が質問のscope_groupsに含まれない → U（適用外）
含まれ、yes_idsにも載っている         → Y（はい）
含まれ、yes_idsに載っていない         → N（いいえ）
```

これは未記入の回答をAIに補わせる省略ではない。**適用内で未列挙のIDは、すべて明示的にNoと定義**している。UをNoへ変換してはいけない。例えば「炭酸の泡がありますか？」は飲み物限定で、レンチに対する答えはU。残候補にUが1つでもある質問は出さない。

146問という数を守るためだけに質問を水増ししない。改訂時には分離不能な候補、重複ID、壊れた参照、意味の食い違いを検査する。機械的な分離検査は、質問の自然さを人が確認する試験の代わりにはならない。

## 3. 推論エンジンと質問選択

### 3.1 役割分担

```text
ESP32: 画面・タッチ・ローカル予備動作・コーヒーカウント
    ↓ 自社HTTPS API
ゲームサーバー: 状態・カタログ・候補の整合性・質問選択・勝敗・匿名ログ
    ↓ TypeSafe API
Jev: 残った候補の相対推測、出題可能な質問からの選択
```

Jevは自由な質問文を生成するのではなく、事前定義された選択肢への`Choice`を使う。公式資料は最大255選択肢、選択結果、各候補の確率、confidenceを説明している。[S2] **本ゲームでJevが必ず他の方法より強い、という実測結果はまだない。** 完全な属性表があるゲームはルールだけでも解ける。Jevは必須の秘密能力ではなく、比較・評価できる差し替え可能な判断部品にする。

Jevの既知の弱点には計算・数え上げが挙げられている。そのため、候補数・情報量・問数上限・スコアの算術はコードで処理する。[S5]

### 3.2 候補集合の更新（正本ロジック）

初期集合Sは選択モードの`item_ids`。質問qにYesなら`S = S ∩ yes_ids(q)`、Noなら`S = S − yes_ids(q)`。質問はSの全候補が適用範囲内の場合だけ出す。skipはSを変更しない。undoでは元のモードから有効な履歴を再生してSを再構築する。

Jevの推測値だけを理由に、属性上矛盾していない候補を削除しない。逆に、正本の回答と矛盾する候補を、Jevが高確率を返したという理由で復活させない。

正しく二分される質問では、通常のYes/NoだけでSは空にならない。S=0になった場合は、データ版の不一致、不正な質問、状態破損などをまず疑う。`STATE_INCONSISTENT`を表示し、直前の安定状態へ戻す。存在しない答えを生成しない。

### 3.3 出題候補の作り方

質問qは次をすべて満たすこと。

1. Sの全候補が適用範囲内である。
2. Yes集合とNo集合の両方が空ではない。
3. このセッションでskipされていない。
4. 候補の区別に寄与する。同一のYes分割になる質問は、短い表示文・ID順を優先して1つにまとめる。

すでに答えた質問は、S上で片側しか残らないため自然に除外される。防御的に出題履歴でも確認する。

### 3.4 情報量と問数ガード

ルール基準ではS内を等確率とし、質問qの分岐確率`r = |S_yes| / |S|`から次を計算する。

```text
H(q) = −r log2(r) − (1−r) log2(1−r)
```

高いほど均等に候補を分ける。ただし1回の分割がよくても、その後の質問が足りない場合があるため、付録Bの`greedy_height(S, blocked)`で残りの最悪深さを確認する。これは**最適な質問木の数学的証明ではなく、実行可能な基準ルートの深さ**である。

```text
G(S)=0                            if |S|<=1
G(S)=999                          if 有効な分割質問なし
G(S)=1+max(G(S_yes),G(S_no))       for 情報量最大の基準質問

安全条件: 1+max(G(S_yes),G(S_no)) <= 残り質問数
```

安全条件を満たす質問群から、最大情報量との差が0.20bit以内のものを選び、最大8問をJevへ渡す。並び順は情報量降順、表示文の長さ昇順、質問ID昇順。丸め誤差対策として比較時に12桁相当で丸める。

skipにより安全な質問がなくなった場合は、現在の最良質問を使う。分割自体が不可能なら、残候補の中から最終予想へ進む。このとき`certainty_reason=insufficient_information`とし、一意に分かったふりをしない。

### 3.5 Jevの質問選択

最大8問の安全な質問候補について、Jevは「今の回答履歴で、分かりやすく自然な次の質問をどれにするか」を選ぶ。候補数の計算、情報量計算、自由な質問追加は任せない。

同じ意味・同じ分割の質問を続けて聞かない。Jevが候補外のIDを返す、確率の形式が壊れている、時間切れになる場合は、基準質問の先頭を採用する。意図的に無意味な質問や誤答を混ぜてゲームを演出しない。

### 3.6 最終予想

- `|S|=1`なら唯一の候補を予想する。これは条件一致であり「実世界の正解率100%」ではない。
- 問数上限または有効質問なしで`|S|>1`なら、検証済みJev分布の最大候補を予想する。
- Jev分布がない場合は、セッションの固定seedと候補ID順に基づいて同率から1つ選ぶ。再送のたびに予想を変えない。
- 予想候補とそのときの分布を固定して保存し、最終Yes/Noの後で都合よく書き換えない。

### 3.7 表示する「確率」

Jevの`probabilities`と`confidence`は別の項目である。confidenceは確率分布の形から計算する指標であって、画面で単純に「正答率」と呼ばない。[S3]

表示語は`AIの予想 42%`とし、HELPに「候補間の推測の割合です。実際の正解率を保証するものではありません。」を表示する。生のJev推測と、ルール基準の均等割合を混ぜて同じ指標と呼ばない。

候補が1つなら`条件に合う候補は1つ`を表示。通信障害でJevが使えなければ`候補 4こ / ルール対戦`と表示し、架空のAI確率アニメーションを出さない。円グラフの動きは実際の値の補間だけとする。

## 4. Jev連携の詳細

### 4.1 確認できた仕様と固定方針

2026-09-19時点の公式モデル資料は`jev-1.13.0`を掲載している。`jev-latest`は更新で実体が変わるため、再現テストでは`jev-1.13.0`を使い、実応答のmodelを保存する。利用できないときに架空の版へ置換しない。英語が主な学習言語と説明されているため、質問意味と候補名は英語を添え、日本語の画面文言とは分ける。[S4]

公式HTTP形は、`POST https://api.typesafe.ai/v1/systemone`、Bearer認証、`state / model / questions`。Choiceには`type / instructions / criteria`、応答には`answers`配下の`choice / probabilities / confidence`がある。[S6]

これは自社ゲームAPIとは別である。ESP32にTypeSafeの秘密鍵を入れず、ブラウザーから直接呼ぶ構成も作らない。APIキー利用権限は本書では確認していない。キー未提供時に実APIの試験を成功扱いにしない。

### 4.2 モデルに渡す情報

`state`に入れてよい情報は、ルール版、モード、現在の候補説明、ユーザーの有効回答履歴、出題済み/skip情報、今コードが作った質問候補、残り問数。次は送らない。

**秘密の答え、候補一覧で閲覧したカード、画面のスクロール位置、滞在時間、社員名、個人アカウント、天気地点、メールアドレス、コーヒーの個人別履歴。**

特に、開始前にプレイヤーに「答えのカードをタップさせてサーバーに送る」方式は禁止。候補詳細を見ること自体は端末ローカルだけでよい。実装者のテストでは`target_id`を使うが、シミュレーター内部にのみ保持し、Jevリクエストに混入させない。

### 4.3 1回の呼出しで2種類のChoice

1回で`guess`と`next_question`を問い合わせてよい。ただし同一呼出しの質問は独立評価であり、一方の出力をもう一方が読めるわけではない。[S7]

したがって、`next_question`の選択肢は**呼出し前にコードで計算**する。今回返ってくる`guess.probabilities`を読んでから選択肢を計算する実装を、1回の並列呼出しに偽装しない。

| 判断 | criteria |
|---|---|
| guess | Sの全候補ID→名前とカードの説明。最大128 |
| next_question | 安全条件を通った最大8問の質問ID→意味とヘルプ |

質問候補が1問しかなければ`next_question`を省略し、その1問をコードで選ぶ。Sが1候補なら呼出し自体を省略できる。値が計算で確定しているものを無理にAPIへ渡さない。

### 4.4 リクエスト組立て契約

下記は組立て方であり、`state`中の具体候補は実際のSから作る。存在しないSDKメソッドを作らないよう、HTTPアダプターを第一実装とする。既存の公式SDKを利用する場合も契約テストで同じ形を確認する。

```python
payload = {
    "model": settings.jev_model,
    "state": {
        "rules_version": "1.0.0",
        "mode": session.mode,
        "history": [
            {"question": q.meaning_en, "answer": a.answer}
            for q, a in active_history
        ],
        "remaining_candidates": candidate_descriptions,
        "remaining_questions": remaining_question_budget,
        "scope": "Closed catalogue. The secret target is NOT provided."
    },
    "questions": {
        "guess": {
            "type": "choice",
            "instructions": (
                "Choose the most plausible secretly imagined item among these "
                "remaining candidates. Respect the canonical card definitions. "
                "All supplied candidates remain compatible with recorded answers. "
                "Do not claim access to the player's thoughts."
            ),
            "criteria": {i.id: f"{i.name_en}. {i.definition_ja}" for i in remaining_items}
        }
    }
}
if len(safe_questions) >= 2:
    payload["questions"]["next_question"] = {
        "type": "choice",
        "instructions": (
            "Select one clear, natural next yes/no question from the supplied "
            "safe options. The application has already checked information "
            "gain and remaining depth. Prefer understandable wording and avoid "
            "repeating the same distinction. Do not calculate or invent questions."
        ),
        "criteria": {q.id: q.meaning_en for q in safe_questions}
    }
```

意味の正確性を優先し、候補の日本語定義も併記する。英語の候補名だけから現実の別レシピを推測させない。将来完全英訳を追加する場合は、属性表と矛盾しないことを検査する。

### 4.5 応答検証

全Choiceに対して次を確認する。

- 応答`type=choice`、期待したquestionキーが存在する。
- `choice`がそのリクエストのcriteriaに含まれ、最大確率候補と整合する。同率差の許容は1e-6。
- `probabilities`のキー集合がcriteriaと一致し、値は有限数、0〜1。boolを数値として受け入れない。
- 合計と1との差が1e-3以下の場合のみ正規化可。より大きいずれ、NaN、Infinity、負値、未知ID、欠落IDはエラー。
- `confidence`は有限数で0〜1。省略や形式異常を勝手に100%へ補完しない。
- `model`は実際に返った文字列を保存。要求モデルと異なるときは管理ログへ警告。

guessだけ失敗した場合はランキングをルール基準にし、next_questionだけ失敗した場合は基準質問を使う。どちらかの失敗でコーヒーカウンターを停止しない。

### 4.6 タイムアウト・費用・運用制限

以下は本製品の設定値であり、TypeSafeのSLAではない。

| 設定 | 初期値 |
|---|---:|
| Jev 1ターン総時間上限 | 3,000ms（接続・読取り・再試行を合算） |
| Jev同一操作の試行 | 最大2回。残り時間がない場合は再試行しない |
| バックオフ | 200〜600msの乱数。Retry-Afterが予算を超える場合は待たずフォールバック |
| 端末→自社APIの待機上限 | 6,000ms |
| 連続失敗で回路を開く条件 | 3回失敗、60秒休止。次の1回で復帰確認 |
| 1デバイス・1日API試行予算 | 500回（設定変更可能） |
| 1デバイス同時セッション | 1つ |
| Jev処理同時数 | 初期2。超えた分はルール処理へ切替え、無制限に待たせない |

通常は開始時と有効な各回答の後に最大1回で、undoや再試行がなければ`最大質問数+1`回以下。早期確定・キャッシュ・質問1択で減る。undo2回・skip2回まで含めると論理呼出し上限は`Qmax+5`、再試行を含む試行上限はその2倍。全操作を同じイベントで二重計上しない。

401/403相当は認証・権限異常として再試行せず通知、422は開発不備として記録、429/529や一時的な5xxは上限内でバックオフする。[S6] 日次の費用は実際のusageと契約単価からサーバーで集計する。固定の「1ゲーム○円」をUIへ埋め込まない。

### 5.4 入力処理

- Yes/Noは押して離した1回で1回答。長押しの繰返しイベントで連続回答しない。[S9]
- クリック受理と同時に両回答ボタンを無効化し、`question_token`を消費済みにする。
- 次の質問が早く来ても、画面更新後に指が全て離れたことを確認してから入力を再有効化する。
- 押したまま画面を切り替えて次問へNoが入る、同じ操作の再送で2問進む、といった事故を防ぐ。
- コーヒーの＋1は別キュー。素早く2回押せば2杯を記録する既存仕様を維持する。

### 5.5 演出と確率表示

応答直後に120〜180msの小さな反応を出す。通信待ちは固定時間の演出で引き延ばさない。初期設定はライブの最有力候補1つを補助情報に表示し、最終結果には上位3候補と「その他」を表示する。候補数が少なければ存在する数だけ表示する。

途中表示を隠す`show_live_prediction=false`も設定可能とする。表示に影響されて対象を変更しないよう開始説明を守る。表示％は最大剰余法などで合計100に整え、元のfloat値は変更しない。ルール処理時は％表示せず候補数を出す。

ブザーは任意の短い操作音のみ。初期値はOFF。音声会話や読み上げは実装しない。

既存リポジトリ構成がある場合は名前を対応づけ、同じ機能の第2実装を乱立させない。ファームは既存のArduinoまたはESP-IDFを継承する。以前の段階1資料は動作済み初期化の保全を最優先としており、Waveshare配布デモと別系統のライブラリを部分的に混ぜない方針である。[P1]

サーバー新設時の標準案はPython 3.11以上、FastAPI、SQLite、非同期HTTPクライアント。具体的な依存版は実装時に取得・固定し、ロックファイルをコミットする。既存の適切なサーバーがある場合、同じAPI契約とテストが満たせれば再利用できる。サーバーを既に用意したと仮定しない。

### 6.2 タスク間の分離

GUIタスクは表示とイベント投入だけ、通信タスクはHTTPSと再送、ゲーム制御部は状態遷移を担当する。通信応答は所有権を明確にしたメッセージとしてGUIへ渡す。ネットワークタスクから破棄済みLVGLオブジェクトを更新しない。`session_id + revision`が現在の画面と異なる遅延応答は捨てる。

ゲームの待機・エラー・終了で、コーヒーのRAMカウントを0へ戻さない。ゲーム起動のために画面全体を再初期化して、既存のタイマーやカウンターを再生成しない。

### 6.3 オフライン方式

本体に同じカタログをコンパイルし、候補集合と情報量最大の基準質問をローカルで計算できるようにする。PC側検査コードは参照用で、PythonをESP32へ載せる意味ではない。C/C++へ移植する。候補bitの順番はcatalog.itemsの配列順（D01をbit0、T32をbit127）に固定し、16バイト化する場合は各バイトの下位bitから順に格納する。scopeはD/F/O/Tをbit0/1/2/3に対応させる。初期版のローカル処理はJevの安全候補内ランダム選択を再現する必要はなく、決定的な基準質問を使う。

既存のオンラインゲーム中にサーバーへ届かなくなった場合は、`同じゲームを端末で続ける`と`再接続`を表示する。端末で継続を選んだら、そのセッションは最後までローカル所有とし、途中で戻って二重に採点しない。復旧時はオンライン側を`aborted/network_handoff`で閉じ、端末結果は別の`local_session_id`でローカル集計に保存する。v1ではローカル対戦の中央ランキング同期を実装しない。

Jevだけが落ち、ゲームサーバー自体は動いている場合は、サーバーがルールへ切替え、同じオンラインセッションを継続して`mixed`集計とする。この2種類の障害を区別する。

## 7. 自社ゲームAPI契約

### 7.1 共通仕様

ベースパス`/api/v1/esper`。JSON/UTF-8。認証はデバイスごとのBearerトークン。トークンからdevice_idを確定し、クライアントが任意のdevice_idを名乗って別端末のセッションにアクセスできないようにする。

UUIDは正規のUUID文字列、日時はUTCのRFC3339、表示上の日付集計はAsia/Tokyoとする。全ミューテーションに`request_id`を含める。セッション操作には`expected_revision`を要求し、同一操作の再送は同じrequest_idと本文を使う。リトライで新しいIDを作らない。

送信本文の上限は16KiB、端末が受け取る通常JSON上限は16KiBとする。カタログ全体を毎回答ESP32へ送らない。カタログは版とハッシュで照合し、UI文言は本体の同版データから引く。

### 7.2 GameViewの全フィールド

| フィールド | 型・許容値 | 意味 |
|---|---|---|
| session_id | UUID | 所属端末に固定 |
| revision | 非負整数 | コミット済み状態更新ごとに増加 |
| mode | easy/normal/hard | 不変 |
| catalog_version | string | 不変 |
| rules_version | string | 不変 |
| phase | processing/question/guess/result/aborted/expired | サーバー状態 |
| answered_count | 0〜モード上限 | 有効なYes/No数 |
| max_questions | 5/7/10 | モード依存 |
| skip_count | 0〜2 | 累計受理skip数 |
| undo_count | 0〜2 | 累計受理undo数 |
| remaining_count | 1〜128 | 残候補数 |
| engine_bucket | jev/rule/mixed | 実際に使った処理。後から偽装しない |
| question | object/null | question時のみ：id、token(UUID)、turn_index |
| prediction | object/null | candidate_id、probability(number/null)、source(jev/rule/exact)、certainty_reason |
| top_candidates | array | 最大3件。candidate_id、probability(number/null) |
| result | object/null | result時：outcome、self_reported=true、accepted_at、quality |
| processing_request_id | UUID/null | 処理中の操作 |
| notices | string[] | `RULE_FALLBACK`等の列挙値。任意HTMLは禁止 |
| expires_at | RFC3339 | 最大寿命 |

`certainty_reason`は`model_guess / exact_match / insufficient_information / rule_tie`。`quality`は`self_reported / invalid_target / inconsistent_reveal / unknown`。未使用のobjectはnull、arrayは空配列で返す。`question.token`は各新規出題時に新しい値を作り、undoで再表示する場合も新しい値を作る。

### 7.3 エンドポイント一覧

| Method / path | 入力 | 正常応答 | 主な制約 |
|---|---|---|---|
| GET /bootstrap | なし | 設定・catalog_version・sha256・modes・server_time・api_version | 認証必須。秘密キーは返さない |
| POST /sessions | request_id,mode,catalog_version,rules_version | 201 GameView / 処理中は202 | 同端末の有効ゲームがあれば409 |
| GET /sessions/{id} | なし | 200 GameView | 他端末は404扱い |
| POST /sessions/{id}/answers | request_id,expected_revision,question_token,question_id,answer | 200 GameView / 202 | answerはyes/no/skipのみ |
| POST /sessions/{id}/undo | request_id,expected_revision | 200 GameView / 202 | 有効な直前Yes/Noを1つ戻す。最大2回 |
| POST /sessions/{id}/verdict | request_id,expected_revision,is_correct | 200 resultのGameView | phase=guessのみ。確定後は変更不可 |
| POST /sessions/{id}/reveal | request_id,expected_revision,reveal_kind,candidate_id | 200 GameView | verdictの後だけ。任意 |
| POST /sessions/{id}/abort | request_id,expected_revision,reason | 200 GameView | reason=user_exit/idle/network_handoff |
| GET /stats?period=today\|week\|all | query | 各mode×engineの集計 | 個人名なし。ISO週は月曜開始 |

`reveal_kind`は`candidate / not_in_catalog / forgot / skipped`。candidateの時だけcandidate_idが必須で、他はnull。candidate_idは当該モードの初期集合内。Noの後で予想と同じIDを申告した場合は`inconsistent_reveal`とし、プレイヤーを責めず集計対象外にする。

### 7.4 回答リクエスト例

```json
  "expected_revision": 3,
```

### 7.5 競合・再送・非同期処理

サーバーは`device_id + request_id`に一意制約を持つoperationを作り、要求本文のハッシュ、状態、結果を保存する。同じID・同じ本文なら保存済み応答を返す。同じID・異なる本文なら409 `IDEMPOTENCY_CONFLICT`。処理中の同じIDなら202と`Retry-After: 1`、現在のGameViewを返す。

処理手順は、(1)短いトランザクションで所有者・revision・question_tokenを検証しoperationと`phase=processing`を保存、(2)DBトランザクションの外でルール/Jevを計算、(3)別の短いトランザクションで状態・応答・ログをまとめてコミット、の順とする。DBロックを握ってJevを待たない。

端末は202時に1秒間隔でGETを最大6回行い、その後は通信復旧画面へ進む。違う回答を追加送信して待ち行列にしない。サーバーが再起動してprocessingが残った場合は、30秒以上古い操作を回収し、記録済み入力から**Jevを再呼出しせずルールで確定**する。表示上はmixed/ruleへ正しく分類する。

### 7.6 エラーの全列挙

| code | HTTP | UI・復旧 |
|---|---:|---|
| UNAUTHORIZED | 401 | 通信設定を管理者へ確認。ローカル動作は継続可 |
| SESSION_NOT_FOUND | 404 | 新規ゲームへ。別端末所有もこの応答 |
| ACTIVE_SESSION_EXISTS | 409 | 既存ゲームを再開するか終了する |
| REVISION_CONFLICT | 409 | GETで同期。回答を別問へ付け替えない |
| STALE_QUESTION | 409 | GETで同期。古いタッチを再解釈しない |
| IDEMPOTENCY_CONFLICT | 409 | 開発・状態異常として記録。自動再送しない |
| CATALOG_MISMATCH | 409 | オンラインゲーム停止、同版本体ルールのみ可 |
| INVALID_PHASE | 409 | GETで正しい画面へ |
| INVALID_INPUT | 422 | 不正なID・型・answer・上限違反。自動補正しない |
| RATE_LIMITED | 429 | 自社API保護。一定時間後再接続かローカル |
| SESSION_EXPIRED | 410 | 勝敗なしでHOME |
| STATE_INCONSISTENT | 500 | ゲームのみ停止、コーヒーは継続 |
| SERVICE_UNAVAILABLE | 503 | ローカル継続を案内 |

共通エラー本文は`{code,message_ja,retryable,request_id,current_revision}`。内部例外、APIキー、SQL、他端末IDを返さない。Jev単体の障害は原則として自社APIの500にせず、正常応答に`RULE_FALLBACK`を載せる。

### 7.7 bootstrap・stats・設定値の厳密化

bootstrapの全フィールドは次のとおり。APIキーやWi-Fiパスワードを返すフィールドは存在しない。

```text
api_version: "1"
rules_version: "1.0.0"
catalog_version: "ai-esper-ja-1.0.0"
catalog_sha256: 64桁の小文字hex（配布catalog.jsonのバイト列）

  show_live_prediction: boolean = true,
  buzzer_enabled: boolean = false,
  dim_after_seconds: integer = 45,
  exit_after_seconds: integer = 120,
  max_session_seconds: integer = 900,
  max_skips: integer = 2,
  max_undos: integer = 2,
  daily_provider_attempt_limit: integer = 500

```

これらの設定をゲーム画面から任意に変更する管理APIはv1で公開しない。サーバーの設定ファイルと端末ビルド設定で管理する。server_timeと既存RTC/NTPを整合させるが、ゲーム開始のたびに時刻を大きく巻き戻さない。

端末の週次・全期間統計はサーバー接続時だけ取得する。ローカルゲームは別欄に件数を表示し、中央集計と足し合わせて同じ値と見せない。

## 8. 状態遷移・履歴・取り消し

| 現状態 | イベント | 次状態 | 備考 |
|---|---|---|---|
| 未作成 | start | processing→question | 残候補=モード初期集合 |
| question | yes/no | processing→question/guess | 履歴保存後、候補と質問予算を更新 |
| question | skip | processing→question/guess | 問数不変、skip_count+1、質問をブロック |
| question/guess | undo | processing→question | 最後のYes/Noを無効化、履歴から再構築 |
| guess | verdict | result | 予想と結果を一度だけ確定 |
| result | reveal | result | 品質情報更新。推論は再実行しない |
| question/guess/processing | abort | aborted | 処理中ならキャンセル世代を進め、遅延結果を破棄 |
| 有効状態 | idle/期限切れ | expired | 集計対象外 |

undo自体ではJevを再呼出しせず、履歴にある当時の質問を再表示する。改めて回答された時だけ通常の更新処理を行う。

undoでは、取り消したYes/No以降にあるskipも無効化し、その時点へ戻る。ただし救済操作の回数自体は累積し、undoで使用回数を巻き戻さない。無効化されたskipの質問は再び出題可能になる。履歴行は削除せず`active=false`にする。

端末は現セッションの履歴を保持し、同じ初期集合・カタログでサーバーのremaining_countを再計算して照合できる。不一致時はローカル推測で上書きせず、GETで同期し、繰り返す場合はデータ不一致として停止する。

### 8.1 永続化の最小テーブル

| テーブル | 主キー・必須列 |
|---|---|
| devices | device_id、token_hash、enabled、created_at |
| sessions | session_id、device_id、mode、catalog_version、rules_version、revision、phase、created_at、expires_at、last_activity_at、engine_bucket、seed、current_question_id、question_token、guess_id、guess_distribution、outcome、quality |
| answers | answer_id、session_id、request_id、question_id、answer、active、sequence_no、created_at |
| operations | device_id+request_id、payload_hash、status、session_id、response_json、created_at、updated_at |
| inference_calls | call_id、session_id、request_id、model_requested、model_actual、status、latency_ms、input_tokens、attempt_no、question_source、ranking_source |
| reveals | session_id（一意）、kind、candidate_id/null、created_at |

候補集合は履歴から再現できるが、読み取り高速化のためbitsetのスナップショットを保存してよい。snapshotにはcatalog_versionとrevisionを必ず付ける。集計はsessionsの確定結果から計算し、verdict再送のたびに加算する実装にしない。

SQLiteは初期の単一サーバー構成用。複数プロセス/複数インスタンスへ拡張する場合は、operationの所有とリースを共有DBで排他できる方式へ変更し、同じ受入試験を実行する。

### 8.2 端末側の保存と再起動

端末の永続状態は`schema_version / generation / catalog_version / payload / crc32`のレコードとし、A/Bの2つのスロットに交互に保存する。payloadのJSONを同じUTF-8・改行なしの規則で符号化してCRC32を求める。CRCは破損検出用で、署名や改ざん対策ではない。起動時はCRCと版が正しい最大generationを採用する。

保存するのは、現在のオンラインsession_id、最新GameViewのrevision、モード、セッションseed、有効回答履歴、skip/undoの累計、未完了のrequest_idと本文、未送信の最終verdict、ローカル集計だけ。フレーム描画や確率アニメーションごとにFlashへ書かない。状態が確定したタイミングで保存し、電源断試験を行う。

オンライン操作は**送信前にrequest_idと本文を保存**し、結果が確定して保存できたらpendingを消す。再起動後はGETで同期してから、未確定の同一操作だけを同じIDで再送する。古いquestion_tokenを新しい質問のtokenへ付け替えない。

未送信verdictは通信失敗のたびに勝敗を増やさず、端末に1件として保持する。サーバーのセッションが期限切れなら中央集計へ後付けせず、`同期できなかった結果`としてローカル記録に残す。pendingを64件超えて新規作成する場合は、ゲーム開始を止めて`記録がいっぱいです`を表示する。黙って古い未送信結果を捨てない。既存コーヒーイベントの保存領域をゲーム用で上書きしない。

CRC不一致で両スロットが読めない場合はゲームの再開を中止し、コーヒー機能は既存の独立した保存領域から復旧する。ゲームの破損を理由に端末の全設定を工場初期化しない。

## 9. 容量・日本語・電源

### 9.1 設計上のメモリ予算

Flash16MBを全部自由なファイル領域と考えない。アプリ、OTA用区画、設定、データ領域の配分はパーティション表による。[S10] 既存区画を無断で変えたり、NVSごと全消去してWi-Fi設定を失ったりしない。

| 用途 | 目標予算・扱い |
|---|---|
| 全カタログJSON | 生成した最小JSONの実測は検証結果欄を参照。約100KiB以下を目安 |
| ファーム内ローカルゲームデータ | 表示文＋128bitのYesマスク＋scope＋ID。英語のモデル説明は端末では省略可能 |
| 日本語フォント | 必要文字だけのサブセット。22/28px等、実測して総量1.5MiB以下を目標 |
| アイコン | 4分野共通の単純図形を基本。128枚のフル画面画像は作らない |
| 1枚のRGB565画面 | 480×480×2=460,800B。ダブルバッファなら921,600B（計算値） |
| ゲームの候補bitset | 128bit=16B。質問ごとのYesビット表は146×16=2,336B（計算値） |
| 1回の端末API JSON | 16KiB以下 |
| 端末結果待ち行列 | 最大64件。勝敗の最小データだけ、巨大なAPI応答を保存しない |

LVGL・通信・TLS・フレームバッファの実際の配置を測定し、PSRAMがあるから内部RAMも無制限だと考えない。ゲーム追加後のheap最小値、最大連続空き、PSRAM使用、リークをログで比較する。具体的なアプリ領域の不足がある場合は、まず素材削減とデータ区画への移動を検討し、移行前バックアップと戻し方を記録する。

### 9.2 フォント

LVGLはUTF-8を扱えるが、フォントに文字がないと日本語は表示できない。[S11] この設計書の全`name_ja / definition_ja / text_ja / help_ja / UI固定文`からUnicode文字集合を抽出し、利用許諾を確認した日本語フォントを**実装環境で取得**して変換する。フォントファイルは本納品に同梱しない。

JSONのバイト数で文字数を切らない。質問は28pxを基本とし、実際の字幅・禁則・行間で収まらない場合は26pxへ縮小して最大3行、長い候補名は結果画面で2行、詳細説明は独立したスクロール領域。省略記号でYes/Noの条件そのものを欠落させない。

### 9.3 電源と省電力

1500mAhの稼働時間は、ゲームの通信頻度、画面の明るさ、実回路で変わる。本書では「1日持つ」と保証しない。USB給電で機能試験し、次に電池駆動で実測する。USB側の電流をそのまま3.7V電池側の電流として換算しない。

ゲーム中はWi-Fi接続を維持し、画面応答のため深いスリープへ入れない。無操作45秒の減光、120秒の終了後に、既存HOMEの省電力方針へ戻す。画面OFFからのタッチ復帰や電池％取得は、ドライバー・回路の対応を実測してから有効化する。

充電用差込口、ケースのボタンアクセス、電池寸法の余裕はB案の機械設計側で確認する。ソフトの仕様から未検証の電池安全性・連続充電可否を断定しない。

## 10. 安全性・プライバシー・ネットワーク

HTTPSではサーバー証明書検証を有効にする。ESP32の公式HTTPクライアントは証明書または証明書バンドルを使う検証方法を案内している。[S12] `setInsecure()`相当を本番の恒久対応にしない。時刻不明で検証できない場合は、時刻同期を試み、失敗時はローカル対戦へ戻す。

端末トークンは本機のゲーム操作のみ許可し、管理APIやTypeSafeの全権限を与えない。ログではAuthorizationを伏せる。サーバーのCORSを全許可する必要はなく、端末にはブラウザー由来のCORS回避は不要。ユーザー入力はenum/IDだけを受け付け、任意の質問文やモデル指示を端末から送信させない。

初期のデータ保存方針は、回答履歴・推論呼出しのメタデータを30日、匿名集計を180日。原文リクエスト/応答の保存は開発時のみ明示有効化し、7日で削除する。個人名や人別のコーヒー回数は保存しない。公開掲示に使う統計は自己申告であると示す。これは製品側の保存設計であり、外部API事業者の保存方針についての保証ではない。

APIアクセス数・同時実行数・要求サイズに上限を設ける。カタログの文字列は信頼する配布物からのみ読み込み、Web由来の自由文を実行指示として渡さない。Jevの公式資料も敵対的な入力が判断へ影響し得ると説明している。[S5]

## 11. 統計と改善

統計の分母は`ai_win + human_win`の有効な確定ゲーム。aborted/expired/invalid_target/inconsistent_revealを除外する。`jev / mixed / rule`を分け、さらにEASY/NORMAL/HARDで分ける。Jevを1回も正常利用していないセッションをjevにしない。唯一候補で呼出し省略したことだけではmixedへ落とさない。

表示例は`本日：AI 8勝 / 人 3勝（自己申告）`。0ゲームなら`まだ記録がありません`。割り算の0除算を避ける。週次は日本時間の月曜0時開始、開始時刻と終了時刻が日をまたぐ場合は終了時刻の営業日へ集計する。

改善指標は、モード別の完了率、平均/最大質問数、skipされた質問、undo率、予想一致率、API成功率、フォールバック率、P50/P95のタッチ後待ち時間。任意の正解申告がある分についてだけ候補別の混同行列を作る。学習のためにユーザーの誤回答を、そのまま正本カタログの事実に上書きしない。

自動でJevの重みが学習・変更されるという説明をしない。v1の改善はカタログ・質問の書き方・候補集合・UI・選択条件の版管理で行う。変更する場合は新しいcatalog_versionを発行し、既存セッションは古い版で終了させる。

### 11.1 比較試験

同じカタログ・同じ対象・同じ模擬回答条件で、ルール基準とJevありを別々に測定する。基準が100%解ける規範回答だけを使って「Jevが強い」と証明したことにしない。実際の差は、質問の分かりやすさ、スキップの少なさ、回答揺れ、少ない問数での予想、通信待ち、再遊びの意欲も含めて評価する。

Jevのみの意味推論を調べる実験を将来追加する場合は別engine_versionとし、v1の属性ガードを無断で外さない。

---

### 11.2 遊びとしての難しさについて

この標準ルールは、十分な質問を正確に答えれば端末が当てられるよう設計している。したがって、「人間が正直に答え、完全な対応表の中から選んでも、半分はAIが外す」というバランスにはしない。主な楽しさは、頭の中のものへ質問が近づくこと、候補が絞れること、短時間で何問かに収まることである。

人間の勝率を演出するために意図的な誤答を入れない。難易度別に対象が増え、skip・回答解釈の違い・問数上限で情報が足りない場合に外れることはある。短い固定問数でAIへ挑戦する追加ルールはv1の対象外とし、本書の問数・成績と混ぜない。

# 付録B. 参考検査プログラム

Python標準ライブラリだけを使用する。`verify_catalog.py`と同じフォルダーに`catalog.json`を置き、`python verify_catalog.py`で実行する。`-O`を付けてassertを無効にしない。成功時に`validation_report.json`と`golden_cases.json`を生成する。コードは**参考検査用**であって、APIサーバー・ESP32ファームの完成実装ではない。

<!-- BEGIN:verify_catalog.py -->
```python
#!/usr/bin/env python3
"""Offline reference verifier. No Jev calls and no hardware tests.
Use: python verify_catalog.py [catalog.json]
"""
from __future__ import annotations
import hashlib, itertools, json, math, random, statistics, sys
from functools import lru_cache
from pathlib import Path

def main(path: Path) -> dict:
    raw=path.read_bytes(); c=json.loads(raw)
    ids=tuple(x['id'] for x in c['items']); idset=set(ids)
    questions={q['id']:q for q in c['questions']}
    assert len(idset)==len(ids)==128
    assert len(questions)==len(c['questions'])==146
    yes={k:frozenset(q['yes_ids']) for k,q in questions.items()}
    scope={k:frozenset(i for i in ids if i[0] in q['scope_groups']) for k,q in questions.items()}
    for k,q in questions.items():
        assert yes[k]<=scope[k]<=idset
        assert 0<len(yes[k])<len(scope[k])
        assert len(q['text_ja'])<=32 and q['meaning_en'] and q['help_ja']
    signatures={i:tuple('U' if i not in scope[k] else 'Y' if i in yes[k] else 'N' for k in questions) for i in ids}
    collisions=[list(p) for p in itertools.combinations(ids,2) if signatures[p[0]]==signatures[p[1]]]
    assert not collisions
    def entropy(p):
        return -sum(v*math.log2(v) for v in p if v>0)
    def eligible(s:frozenset,blocked:frozenset=frozenset()):
        out=[]
        for k,q in questions.items():
            if k in blocked or not s<=scope[k]: continue
            y=s&yes[k]; n=s-y
            if not y or not n: continue
            h=entropy((len(y)/len(s),len(n)/len(s)))
            out.append((k,h,y,n))
        out.sort(key=lambda a:(-round(a[1],12),len(questions[a[0]]['text_ja']),a[0]))
        return out
    @lru_cache(maxsize=50000)
    def greedy_height(s:frozenset,blocked:frozenset=frozenset()):
        if len(s)<=1: return 0
        choices=eligible(s,blocked)
        if not choices:return 999
        _,_,y,n=choices[0]
        return 1+max(greedy_height(y,blocked),greedy_height(n,blocked))
    def shortlist(s:frozenset,remaining:int,blocked=frozenset()):
        allq=eligible(s,blocked)
        if not allq:return []
        safe=[x for x in allq if 1+max(greedy_height(x[2],blocked),greedy_height(x[3],blocked))<=remaining]
        if not safe:
            return [allq[0]]  # Information is insufficient; do not claim certain success.
        best=safe[0][1]
        near=[x for x in safe if x[1]>=best-0.20-1e-12]
        # Deduplicate same YES partition; keep meaning-changing complementary questions distinct.
        seen=set(); unique=[]
        for x in near:
            if x[2] in seen:continue
            seen.add(x[2]);unique.append(x)
        return unique[:8]
    report=dict(catalog_version=c['catalog_version'],source_sha256=hashlib.sha256(raw).hexdigest(),
                candidate_count=len(ids),question_count=len(questions),matrix_cells=len(ids)*len(questions),
                signatures_unique=len(set(signatures.values())),collision_pairs=collisions,
                test_scope='Python reference only. Jev / firmware / display / power are NOT tested.',modes={})
    fixtures=[]
    for mode,config in c['modes'].items():
        targets=tuple(config['item_ids']); maxq=config['max_questions']; lengths=[]
        for target in targets:
            s=frozenset(targets); answers=[]
            while len(s)>1 and len(answers)<maxq:
                opts=shortlist(s,maxq-len(answers))
                assert opts, (mode,target,'no_question')
                k,_,y,n=opts[0]
                answer='yes' if target in y else 'no'
                s=y if answer=='yes' else n
                answers.append({'question_id':k,'answer':answer,'remaining_count':len(s)})
            assert s==frozenset([target]), (mode,target,answers,s)
            lengths.append(len(answers))
            fixtures.append(dict(mode=mode,target_id=target,answers=answers,expected_guess=target))
        random_games=0
        for seed in range(30):
            rng=random.Random(seed)
            for target in targets:
                s=frozenset(targets); nasked=0
                while len(s)>1 and nasked<maxq:
                    opts=shortlist(s,maxq-nasked)
                    assert opts
                    _,_,y,n=rng.choice(opts)
                    s=y if target in y else n; nasked+=1
                assert s==frozenset([target]), ('random',mode,target,seed)
                random_games+=1
        report['modes'][mode]=dict(candidates=len(targets),max_questions=maxq,
            deterministic_games=len(targets),random_safe_games=random_games,
            canonical_success_rate=1.0,min_questions=min(lengths),max_questions_observed=max(lengths),
            mean_questions=round(statistics.mean(lengths),3),greedy_worst_depth=greedy_height(frozenset(targets)))
    report['reference_game_count']=sum(x['deterministic_games']+x['random_safe_games'] for x in report['modes'].values())
    (path.parent/'validation_report.json').write_text(json.dumps(report,ensure_ascii=False,indent=2)+'\n',encoding='utf-8')
    (path.parent/'golden_cases.json').write_text(json.dumps(fixtures,ensure_ascii=False,indent=2)+'\n',encoding='utf-8')
    print(json.dumps(report,ensure_ascii=False,indent=2))
    return report
if __name__=='__main__':
    main(Path(sys.argv[1]) if len(sys.argv)>1 else Path(__file__).with_name('catalog.json'))
```

# 付録C. このMarkdownだけからデータを取り出す

次のコードを`extract_from_markdown.py`として保存する。同じファイルが既にあり内容が異なる場合は上書きせず停止する。

```python
from pathlib import Path
import re
import sys

source = Path(sys.argv[1])
text = source.read_text(encoding="utf-8")
out = Path("ai_esper_handoff")
out.mkdir(exist_ok=True)
for name in ("catalog.json", "verify_catalog.py"):
    pattern = (re.escape(f"<!-- BEGIN:{name} -->") +
               r"\s*```[a-z]+\n(.*?)\n```\s*" +
               re.escape(f"<!-- END:{name} -->"))
    match = re.search(pattern, text, re.S)
    if not match:
        raise ValueError(f"Embedded block not found: {name}")
    content = (match.group(1) + "\n").encode("utf-8")
    destination = out / name
    if destination.exists() and destination.read_bytes() != content:
        raise FileExistsError(f"Refusing to overwrite different content: {destination}")
    destination.write_bytes(content)
    print(destination)
```
